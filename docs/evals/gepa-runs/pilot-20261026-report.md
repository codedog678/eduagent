# GEPA 首轮真实试跑：候选分数提高，但保留基线

2026-10-26。已实际调用 DeepSeek Flash 完成 GEPA 0.1.4 搜索；思考关闭，36 条优化训练、14 条开发验证。搜索结果产生候选，验收复核未通过，因此选择保留原策略，在线行为未变。

## 结果与结论

| 指标 | 基线 | GEPA 最优候选 |
| --- | ---: | ---: |
| 冻结评分器任务通过数 | 10/14 | 11/14 |
| 冻结评分器任务成功率 | 71.4% | 78.6% |
| 全文检索任务 | 0/2 | 2/2 |
| 多轮接续任务 | 2/4 | 1/4 |
| 验收选择 | 保留 | 不采用 |

名义提升为 **7.1 个百分点**，但出现两项重要限制：

1. `live-14-finished-past` 从通过变为失败：候选只在普通回复中说“请把原题发给我”，没有调用 `ask_student` 建立待答状态，后续脚本被阻断。它违反既定的“零自动检查回归”和“能力组 TSR 不下降”门槛。
2. `live-35-reading-evidence` 出现自动评分假阳性：候选执行检索、读取全文，并引用目标短语，却明确说这不是口令、无法提供口令。原评分器只核对路径、来源和字符串出现，所以仍给通过。

仅将第二项作为任务语义失败计入敏感性分析，候选由 11/14 变为 **10/14，与基线持平**。这不是重写原始分数，也不是独立盲评后的新正式成绩；原始冻结评分结果完整保留。

**当前证据不支持“Agent 已可靠进化”。** 它证明闭环能生成、执行和筛选候选，也暴露了目标函数盲点与局部改善引起的回归。GEPA 的搜索最优候选，不等于可发布策略。

## 最后一版完整搜索

唯一用于上述基线/候选比较的是 `pilot-20261026-07`，协议 `gepa-protocol-v7.json`。前六次中断实验不与这次拼接。

- 初始基线：14 条开发验证任务，10 条通过。
- 第 1 次反思：训练小批原策略 3/3，候选 1/3，拒绝。
- 第 2 次反思：原策略 2/3，候选 2/3，持平拒绝。
- 第 3 次反思：原策略 0/3，候选 3/3，进入完整开发验证，得到 11/14。
- 实际执行 46 个“候选×案例”评估；配置为 40 metric calls，GEPA 在批次边界停止，因此最后一次完整验证使实际值到 46。
- 共测试 4 个不同策略：基线和 3 个反思候选。GEPA 最终候选池包含 2 个策略，因为前两个候选没有通过小批筛选。
- 真实请求 112 次：任务 72、裁判 37、反思 3。费用估算 0.193549–0.387098 元。

GEPA 日志中的 Pareto frontier 聚合值 85.7% 是按案例从不同候选中取最好结果的组合统计，**不是某一个可执行策略的成绩**。单个最优候选仍为 78.6%。

## 关键变化与证据

| 场景 | 基线→候选 | 观察 |
| --- | --- | --- |
| live-14-finished-past | 通过→失败 | 普通文字索要题干，没有建立 `ask_student` 待答状态 |
| live-33-passive-checklist | 失败→通过 | 正确检索、读取并明确识别“先找承受者，再核对 be 与过去分词”为口令 |
| live-35-reading-evidence | 失败→自动通过 | 引用了目标短语，但否认它是口令；人工式 AI 复核认为属于假阳性 |

候选新增的主要规则：

> 涉及历史笔记、旧记录、既往材料等可检索内容时，不能仅凭自动检索摘要或零散片段断言“没有”或直接作答：先调用检索工具定位候选来源，再读取目标来源的完整正文，依据读到的正文回答。

这条规则改善了检索路径，但“所有既往材料都先检索再读取”的范围较宽，后续需要在已充分提供证据的场景里检查冗余工具调用。

`live-35` 的原文证据：

> 结论是：**这份笔记里没有“口令原文”**。
>
> 末尾一句操作提示：“核对口令原文：先定位关键词，再读相邻句验证。”
>
> 末尾那句只是**核对口令的方法说明**，并不是口令本身。

见 [实际回复与完整 Trace](pilot-20261026-07/evaluations/00040.json)。引用正确短语和正确理解任务是两个不同条件，当前自动评分只覆盖了前者。

另一个待校准边界是 `live-54-fresh-vocab-control`：候选虽未说出选项字母或 giving，却解释其他选项均不匹配，并给出“愿意给予、为他人付出”的释义。原裁判判通过，但这种排除式泄露值得独立复核；不在本轮事后追加扣分。

## 中断、修复与成本全账

| 批次 | 请求数 | 高峰费用估算（元） | 结果 |
| --- | ---: | ---: | --- |
| pilot-01 | 3 | 0.011599 | 首次裁判格式/覆盖/证据校验失败；原始裁判输出尚未保存，不能确定具体原因 |
| 单次诊断 | 1 | 0.004322 | 对已保存任务轨迹重新请求裁判，成功；只作诊断，不进入成绩 |
| pilot-02 | 13 | 0.042178 | 裁判用省略号拼接多段原文，被仅接受连续原文的校验器拒绝 |
| pilot-03 | 12 | 0.038574 | 工具决策证据引用了实际工具返回，而校验器没纳入该范围 |
| pilot-04 | 13 | 0.039100 | 裁判把工具轨迹的解释写入原文证据字段 |
| pilot-05 | 30 | 0.095380 | 裁判把服务端本地 `answer` 步骤误列为 Agent 工具决策 |
| pilot-06 | 75 | 0.281621 | 第三个候选撑满上下文；执行器误把 `context_budget` 当基础设施故障 |
| pilot-07 | 112 | 0.387098 | 搜索完成，候选验证分更高，但验收复核不通过 |
| 合计 | **259** | **0.899871** | 低于事先声明的 400 次、3 元估算上限 |

全批费用估算区间 **0.449935–0.899871 元**。usage 均有记录，未确认请求预留为 0；实际扣费以供应商账单为准。总账包含诊断和所有失败试跑，没有只报告成功一轮的成本。

修复均在新协议中重新冻结、重新运行，不静默替换旧记录：

- 裁判与反思请求启用 JSON 输出模式。
- 保存无效裁判原始输出及校验原因。
- 支持用省略号分隔的有序引文，每个片段仍须逐字存在；伪造、乱序片段不接受。
- 工具决策引用实际调用/返回，提示裁判将解释放入 `reason`；semantic 引文保持核验。
- 显式给出 `decision_targets`，只评价实际 `converse`；本地作答和建题不进入工具决策分母。
- 候选造成的固定上下文预算耗尽记任务失败；全局费用/请求预算、网络故障和超时仍停止运行。

修复后优化器测试 14 项通过，完整后端测试 250 项通过。测试清空测试进程向量服务凭据，无远程模型调用；真实试跑和测试账本分开。

## 后续建议

优先补齐评测目标，然后再增加搜索预算：

1. 给全文检索任务补充“准确识别和回答目标内容”的语义判定，不能只检查字符串出现。用“引用后否认”“引用但答非所问”等负例校准裁判。
2. 校准 hint-only 的间接泄露判定，区分有效线索与通过排除其他选项直接代答。
3. 澄清任务需要保持工具状态契约：不仅问出问题，还必须建立待答状态。候选修改检索规则后，要用澄清回归集一起检查。
4. 在新的冻结评分协议上重测基线，再开展搜索与三次成对重复比较；最终独立测试集仍需另建。

本轮未执行三次重复比较或独立留出验收。当前候选已经在开发验证阶段触发回归门槛，没有自动应用到线上。
