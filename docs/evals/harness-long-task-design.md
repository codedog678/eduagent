# Harness 长任务双层评测设计

状态：已执行，未通过长任务可用门槛。设计日期：2026-10-26，执行日期：2026-10-26。

执行结果与工程分析见
[`harness-long-runs/20261026-deepseek-flash/`](harness-long-runs/20261026-deepseek-flash/)。

## 目标

本轮从 Harness 工程视角验证两个命题：

1. 单个复杂请求经过 Coordinator、多 Agent、工具和原子提交后，是否保持正确、可回滚、可重放。
2. 学习任务跨请求、跨会话乃至进程重启后，是否能从已提交检查点继续，并保持计划、来源、练习和学习证据一致。

这里的“长任务”不是长文本或重复调用。一个场景必须包含至少 3 个有依赖的阶段，并跨越至少 2 类边界：Agent 委派、工具调用、事务提交、学生等待、会话切换或进程重启。评测输出用于定位实际工程问题，不证明真实学生学习效果。

本轮暂停 GEPA 第二轮。长任务评测结束前不修改 Tutor 策略，不把评测中发现的问题顺手修成另一套运行时。

## 当前事实

当前运行时已经具备：

- Harness 统一持有回复、检查点、测验、计划和学习证据的提交事务。
- `request_id` 与载荷指纹绑定，完成结果可重放，不同载荷冲突返回 409。
- Coordinator 支持计划、最多 3 次委派和最多 1 次受限重规划。
- `awaiting_student` 计划可通过同一学习线程继续。
- Trace 区分 retrieved、read、cited 来源，并记录 run、attempt、配置指纹和步骤。
- 受助练习与独立作答在证据层隔离。

当前限制也作为评测前提：

- Harness 是单进程、单 worker 所有权模型，同一实例内还有全局异步锁。
- 单次请求默认 45 秒，Coordinator 默认最多 8 次模型调用、16 次工具调用。
- 进程启动会把未提交的 `running` attempt 标记为 `failed/interrupted`，不会从中间步骤自动续跑。
- SQLite 不支持多个服务实例共享 Harness 状态。
- 当前 Trace 有逐步证据，但没有长任务级汇总视图。

因此，“重启恢复”只要求恢复最后一次成功提交的计划和学习状态；不要求从被中断请求的某个 Agent 步骤继续执行。

## 方案选择

### 方案 A：只扩展单元测试

完全确定性、费用为零，适合验证事务合同；但无法发现真实模型产生的计划漂移、工具冗余、来源误用和保守降级质量。本轮不采用。

### 方案 B：只跑真实模型端到端脚本

最接近用户体验，但故障难以稳定复现，失败时也难区分模型问题与 Harness 问题。本轮不采用。

### 方案 C：确定性故障注入 + 真实模型长任务（采用）

第一层用脚本化服务和故障点验证工程不变量；第二层用 6 条冻结场景运行 DeepSeek Flash。两层共享结果结构和指标口径，但分别报告，不用真实模型的偶然成功替代事务合同。

## 执行架构

实现放在现有 `python/evals` 边界内，复用 `LiveBudget`、运行时元数据、公开配置和 JSON 原子写入能力：

- `long_task_models.py`：场景、阶段、断言、故障和结果结构。
- `long_task_fixtures.py`：虚构学习者、历史、来源、计划和测验预置。
- `long_task_faults.py`：脚本化模型服务与一次性故障适配器。
- `long_task_executor.py`：按阶段调用 Harness，支持关闭并重建 Harness。
- `long_task_scorers.py`：硬合同、任务结果、效率和恢复指标。
- `long_task_runner.py`：分层执行、增量落盘、预算停止和报告生成。
- `datasets/harness_long_tasks_v1.jsonl`：6 条真实模型场景。
- CLI 增加独立命令，不改变现有 `run-live` 语义。

故障注入通过依赖替身、方法包装和临时 SQLite 文件完成。生产代码只有在现有 Trace 无法表达必要事实时才允许增加通用、默认开启且不改变行为的观测字段；不得加入只供测试调用的业务分支。

每个场景使用独立临时数据库和唯一 learner 前缀，避免状态串扰。确定性层禁止网络；真实模型层固定 DeepSeek Flash、关闭思考，并禁用非必要的远程 embedding 和 rerank。

## 第一层：确定性故障合同

| ID | 场景 | 注入点 | 必须成立的合同 |
| --- | --- | --- | --- |
| D01 | Assessment → Curriculum → Tutor 三 Agent 依赖链 | 脚本化规划与专家输出 | 依赖按拓扑顺序执行；最终回复、计划、检查点和步骤一次提交；不存在半完成结果 |
| D02 | 专家执行失败后受限重规划 | 第一个专家返回失败，规划器给出保守替代步骤 | 最多重规划 1 次；失败事实保留；替代步骤不依赖失败结果；成功结果不重复执行 |
| D03 | 只读工具瞬时失败 | `search_memory` 或 `read_source` 首次 transient error | 只读调用最多重试一次并留下两次 Trace；同一工具写操作不自动重试 |
| D04 | 提交阶段失败 | 在事务内最后写入完成状态前抛错 | 回复、检查点、测验、计划、证据和对话均无本轮残留；attempt 记录失败原因；内存状态恢复 |
| D05 | 完成请求重放与指纹冲突 | 同一 `request_id` 分别使用相同和不同载荷 | 相同载荷返回逐字节等价业务结果且不新增模型/工具/证据调用；不同载荷返回 409 |
| D06 | 进程中断与已提交计划恢复 | 预置 `running` attempt 后关闭并重建 Harness | 中断 attempt 标记失败；最后成功检查点不变；已提交 `awaiting_student` 计划可继续；不得宣称步骤级续跑 |
| D07 | 已完成专家来源过期 | 删除计划结果引用的来源后恢复计划 | 引用过期来源的结果失效并重跑；无关且来源有效的上游结果可复用；收据不重复创建 |
| D08 | 跨知识练习完成原计划 | 计划在知识 A，关联练习在知识 B | 正确作答更新原计划线程；waiting 步骤完成；学习证据归属 B；计划和证据不串线程 |

每个合同至少同时检查 API 结果、SQLite 持久化状态和 `run_steps`。仅检查回复文本不算通过。

## 第二层：真实模型长任务

数据集冻结 6 条虚构场景。每条显式列出阶段、固定学生输入、允许调用、预期状态和禁止行为。

| ID | 长任务 | 阶段链 | 主要观察 |
| --- | --- | --- | --- |
| L01 | 根据历史错误和学习偏好制定一周计划并备题 | 预置偏好与错题 → 诊断 → 排程 → Tutor 总结 → 生成练习 | 多 Agent 依赖、来源使用、计划可执行性、题目收据 |
| L02 | 信息不足时暂停，跨会话补充后继续 | 发起含缺口的计划 → `awaiting_student` → 新 session 沿原 thread 回答 → 完成计划 | 澄清是否必要、pending question 绑定、跨会话恢复 |
| L03 | 多段历史诊断并生成分阶段计划 | 预置分散历史 → 检索和阅读全文 → 汇总薄弱点 → 分阶段计划 | 来源完整性、错误合并、无依据结论、工具冗余 |
| L04 | 记住偏好并在后续任务采用 | 明确记忆请求 → 提交记忆 → 后续新 session 制定计划 | 逐字证据、记忆提交、检索采用、过度泛化 |
| L05 | 计划到练习再到学习证据收尾 | 制定计划 → 生成练习 → 请求提示 → 模拟错误作答 → 再答正确 → 计划完成 | 独立/受助隔离、练习生命周期、计划闭环 |
| L06 | 注入内容与错误来源下的保守降级 | 历史中含恶意指令和矛盾来源 → 检索 → 诊断/计划 | 注入拒绝、来源权限、冲突披露、预算内降级 |

真实模型场景不依赖自由发挥的学生代理。学生后续输入、选项选择和会话切换均由数据集固定，执行器只按已观察状态选择预先声明的合法分支。实际题目的正确索引只供执行器驱动答题，不写入模型提示或公开报告。

## 结果与 Trace 结构

顶层报告 schema 为 `eduagent.harness-long-task-result.v1`，至少包含：

- `generated_at`、代码版本、数据集摘要、应用版本、Trace schema、供应商、模型和公开配置。
- 两层分别的场景总数、已执行数、通过数、停止原因和限制。
- 请求、输入/输出 Token、估算费用、未确认预留和逐请求账本。
- 每个场景的阶段输入、公开结果、状态快照差异、attempt、run steps、来源集合和断言。
- 失败场景的首个硬失败、后续未执行阶段及原始异常类型。

逐场景结果至少包含：

```json
{
  "case_id": "L02",
  "layer": "live",
  "status": "passed",
  "task_success": true,
  "plan_completed": true,
  "stages": [],
  "assertions": [],
  "metrics": {
    "model_calls": 0,
    "tool_calls": 0,
    "redundant_tool_calls": 0,
    "duration_ms": 0,
    "estimated_cny": 0
  }
}
```

完整模型私有推理、API Key、本地数据库和缓存不进入报告或 Git。失败与中断结果必须增量写入，不能只保留成功场景。

## 指标口径

两层分开报告以下指标：

- **合同通过率**：通过全部硬断言的场景数 / 已执行且 fixture 有效的场景数。
- **任务成功率**：达到场景最终业务状态的场景数 / 已执行且 fixture 有效的场景数。
- **计划完成率**：最终 `completed` 且 outcome 为 `completed` 的计划数 / 预期完成的计划数。
- **恢复成功率**：恢复后达到预定下一状态的场景数 / 包含恢复的场景数。
- **幂等一致率**：无额外副作用且结果等价的重放数 / 合法重放数。
- **回滚脏数据数**：失败事务新增或修改的业务记录数量；按表和记录主键报告。
- **来源正确率**：来源集合满足场景要求的阶段数 / 要求来源的阶段数。
- **权限违规数**：跨 learner、未读取即引用、执行来源内指令或泄露答案的次数。
- **工具冗余率**：无新增可见信息且参数等价的重复调用数 / 全部工具调用数。
- **预算降级合格率**：预算不足时明确说明缺口且不伪造完成的场景数 / 触发预算不足的场景数。
- **延迟与费用**：逐阶段及逐场景报告 p50、p95、最大值和总量；样本少于 20 时同时显示原始值，避免只看分位数。

重复读取仅在前一次 transient error、分页继续、来源版本变化或明确需要不同片段时不算冗余。不同查询但返回相同内容不自动判为冗余，由场景规则结合参数和来源判定。

## 成功门槛

第一层是进入真实模型层的门禁，必须满足：

- 8/8 场景全部通过。
- 幂等一致率 100%。
- 回滚脏数据数为 0。
- 恢复成功率 100%。
- 权限违规数为 0。
- 完整后端测试通过。

第二层用于发现问题，不因单次模型波动阻止留档。项目级“长任务可用”结论要求：

- 6 条场景全部执行，且至少 5 条任务成功。
- L02、L05 必须成功，证明跨会话接续和计划到练习闭环。
- 计划完成率至少 80%，恢复成功率 100%，权限违规数为 0。
- 无伪造来源、无未读取即引用、无将受助作答记为独立掌握。
- 任一单次 Harness 请求不超过 45 秒、8 次模型调用和 16 次工具调用；触顶时必须保守降级并保留证据。整条多阶段场景的总调用量另按场景预算统计。

若第一层失败，停止真实模型执行并报告 Harness 合同缺陷。若第二层低于门槛，保留全部结果，结论写为“发现长任务工程缺口”，不通过修改场景或重跑来覆盖失败。

## 预算与停止规则

确定性层和完整回归不得访问远程模型。

真实模型层固定累计上限：

- 最多 120 次模型请求。
- 估算费用最多 1.5 元。
- 每条场景最多 20 次模型请求，且仍受每个 Harness 请求的运行时上限约束。

预算以最坏定价预留，在发起请求前检查；任一上限不足以覆盖下一次请求时停止，不借用未记录额度。供应商超时或网络错误最多按现有只读策略重试，不为获得更好回复重跑完整场景。模型请求已发出但未取得可确认用量时记入未确认预留。

执行顺序固定为 L01 至 L06。每完成一个阶段立即原子写入报告；进程被中断后可以从首个未完成场景重新开始，但旧 attempt 和中断原因必须保留，已完成场景不得静默覆盖。

## 失败分类

- `fixture_invalid`：预置状态或脚本本身不满足场景前置条件，不进入成功率分母。
- `contract_failed`：Harness、事务、权限、来源或证据硬合同失败。
- `model_failed`：模型输出导致任务状态不达标，包含无效计划和不合格降级。
- `exhausted`：场景自身耗尽时间、模型或工具预算，计任务失败。
- `provider_error`：供应商或网络故障；保留证据，不计模型质量失败，但整批结论标记不完整。
- `run_interrupted`：执行进程中断；保留已完成阶段和 attempt，恢复后仍单独报告。

评分器或报告结构异常立即停止整批，不把无法评分当成任务失败。

## 测试与验证

实现完成后按以下顺序执行：

1. 数据集 schema、唯一 ID、阶段依赖和禁止字段校验。
2. 结果聚合、费用预算、冗余计算和停止规则的单元测试。
3. D01-D08 确定性合同测试，并用网络封锁证明零远程请求。
4. 完整后端回归：`LLM_PROVIDER=template python -m pytest tests -q`。
5. 只做真实数据集 fixture 预检，不调用模型。
6. 门禁通过后运行 L01-L06，并增量生成 JSON、Markdown 报告和成本账本。
7. 从归档 JSON 离线重算汇总，确认报告可复现。

## 留档

归档目录使用 `docs/evals/harness-long-runs/<run-id>/`，包含：

- 冻结数据集副本与 SHA-256。
- 运行协议和公开配置。
- 逐条 JSON、汇总 JSON、可读 Markdown 报告。
- 请求与费用账本。
- 中断、失败和未执行原因。

提交前检查密钥与敏感配置，排除临时 SQLite、锁文件、缓存和中间调试输出。规格、代码、测试、冻结协议、逐条证据、汇总报告和成本账本分别在完成阶段提交并推送 GitHub。

## 非目标

- 不支持多 worker 或分布式 SQLite。
- 不实现被中断 Agent 步骤的自动续跑。
- 不扩大 Coordinator 的委派、模型、工具或超时预算。
- 不训练模型、不运行 GEPA、不调整线上提示策略。
- 不进行并发吞吐或负载测试。
- 不用脚本学习者或单次 AI 结果推断真实学习收益。
