## 具体原因与对应修改

### 1. 专家输出 schema 与执行契约存在落差

原记录共有 5 次 `expert_result_invalid`，其中 Assessment 4 次、Curriculum 1 次，末次模型停止原因均为 `stop`。在当前实现中，JSON/schema 解析异常会产生 `expert_schema_invalid`，而这 5 次记录指向解析后的额外检查。因此不能笼统称其为“模型没输出合法 JSON”。[专家运行时](../../../python/core/specialist_runtime.py#L43-L70)、[离线提取](evidence.json)。

额外检查包括：task_id 必须匹配当前步骤；来源必须已向该专家提供且仍有效；只有完成状态的 Curriculum 能提议动作；needs_input 必须有问题；completed 必须有 findings 且不得同时要求补充信息。目前不同失败大多折叠为同一个 ValueError 类型，没有字段级原因。

已复现的接口落差是：`AgentResult` schema 接受 `status=completed` 且省略 findings，解析得到空列表，随后运行时拒绝为 `incomplete_expert_result`。这只是可触发失败的机制，不能认定 5 次原结果都缺 findings。[协调模型](../../../python/core/coordination_models.py)、[专家运行时](../../../python/core/specialist_runtime.py#L49-L52)。

建议先修改：

- 增加安全的细分校验码，如 `task_id_mismatch`、`unverified_source_ref`、`completed_without_findings`、`completed_with_question`、`action_not_allowed_for_role`，贯通专家完成、委派结果和 plan_step_failed。记录字段名、角色、步骤和允许来源集合；不保存私有推理或供应商完整响应。
- 为模型使用精简的结果草稿 schema，按 status/role 编码运行时约束。completed 的 findings 非空、needs_input 有问题、Assessment 不包含动作字段。身份和持久化状态由服务端绑定；若兼容旧字段，显式矛盾仍需拒绝。
- 将 `known_source_refs`、`read_source_refs`、剩余模型/工具额度直接列入专家输入，减少模型自行拼接来源、猜测契约的机会。
- 在**已分配的预算内**允许一次带细分错误的修正；例如工具读取后第二次请求产出草稿，若还有第三次额度，用它修正。最后一次请求失败时直接返回明确降级，不能追加请求或悄悄删除错误引用。

收益首先覆盖 4 个场景，但修复后的提升幅度必须经复测确认。保留来源归属、来源有效性和受助证据校验。

### 2. 规划器承担了过多服务端字段，证据校验又混用了文本判断

当前规划器直接生成完整 `LearningPlan`，schema 同时包含 plan_id、status、results、receipts 等执行态字段，随后服务端再丢弃这些字段。输入和输出的职责不够明确。证据槽既由模型声明，又由服务端重新绑定；发生冲突就回退。文本正则还可能将否定句当作缺失声明。[规划创建](../../../python/core/coordinator.py#L143-L174)、[证据绑定](../../../python/core/coordinator.py#L61-L105)。

建议把生成接口改为 `PlanDraft`：只生成目标、任务约束、步骤和必要澄清；计划身份、状态、收据和稳定记忆证据槽由服务端持有。模型引用来源仍要与已提供集合核验，不因字段减少而放宽事实检查。

对于稳定画像是否存在，应以数据库中的结构化槽为准。区分“没有偏好”和“已有偏好，但尚无每天时长”等不同缺口；文本正则不再单独决定事实冲突。若保留旧协议，应识别否定语境，并记录具体冲突槽或字段，而不是只留下 `planner_evidence_conflict`。

这项修改还应避免把模型生成的异常状态填回计划，继续复用现有 DAG、预算、原子提交和回退机制。

### 3. 检索失败主要是资料发现与查询策略问题

L01 的索引存在 4 个 chunk，原查询“时态 错误 tense”“grammar_tenses”以及空查询都没有命中。`grammar_tenses` 是知识范围标识，当前仅作为过滤条件，原文索引中不包含该 ID。冻结错误原文包含“since”“by the time”“过去时”“将来时”；离线查询这些原词能够找到 `l01-error-1` 和 `l01-error-2`。因此本次不是缺失历史或索引未建立。[词法索引与查询](../../../python/core/memory_store.py#L122-L145)、[重放证据](evidence.json)。

L03 则停在更早的环节：规划器要求提供已预置历史及复习时长，但 `planning_facts()` 当前只提供稳定记忆、知识状态和待答问题，没有历史可访问性摘要。规划器无法直接验证是否有历史，提示中的“缺信息先问”容易提前阻断检索。[规划事实输入](../../../python/core/coordinator.py#L56-L59)、[原始 L03 回复](../harness-long-runs/20261027-deepseek-flash/result.json)。

建议优先复用现有词法与历史读取链路：

1. 在规划输入加入当前 learner/knowledge 下的历史存在性、数量及素材可用状态，区分“有记录尚未检查”“没有记录”和“教材未提供”。数量只说明可访问性，不能据此生成能力诊断。
2. 从知识图谱名称、标签和通用术语配置生成查询扩展，不硬编码 `since 2020` 等评测答案。零命中后最多做一次同知识范围的有限历史枚举，复用 `LearningHistory.messages()` 并投影为候选摘要和来源。
3. 枚举与全文读取分别留痕；检索到来源不等于已阅读全文。优先读取至少两条相关原文，保留分页、归属和版本检查。
4. 只有执行必要动作仍缺信息时才提问。每日时长可以影响排程，但不能成为先读取已有历史的前置条件；教材缺失应明确说明，不冒充已检索材料。

空查询当前语义是空集，不能直接解释为“浏览历史”。如需枚举，应设计明确模式和上限，避免混淆相关检索与最近记录。暂不通过打开 embedding/rerank 改变本轮基准；先修复已证实的词法与调用问题。

### 4. 练习动作缺少可行性预检，失败会抹掉有效专家发现

L04 的原回执保存了备题参数：`reading_skimming`、难度 0.3。冻结初始知识状态只有略读的初始估计，没有满足掌握阈值的前置知识。略读要求 `vocab_basic` 与 `grammar_tenses`；按这些参数重放，返回“前置知识尚未满足”。本次证据比既有复测报告更充分，修正了其“动作参数未留存”的判断。原 HTTP detail 仍未归档，原始记录保持不变。[备题门禁](../../../python/core/harness.py#L377-L390)、[动作重放](evidence.json)。

更深的问题是，Curriculum 本身已经成功返回；动作被拒绝后，Coordinator 将整个结果替换成空 findings 的失败对象，Tutor 依赖也随之阻塞。后续重规划又分配一个仅有一次模型额度的 Assessment，结果再次校验失败。[动作执行与异常处理](../../../python/core/coordinator.py#L388-L415)、[预算分配记录](evidence.json)。

建议：

- 将知识前置条件、已掌握集合、当前可练节点作为服务端快照提供给 Curriculum；备题前用同一权威门禁预检，不让模型判断替代执行校验。
- 明确任务必须交付什么。L01、L05 明确要求题目；L04 的冻结成功合同要求记忆与计划采用偏好，并没有必须备题。对于可选动作受阻，可以保留有效发现，继续交付遵守偏好、说明前置限制的计划；必须备题的任务受阻则仍为 partial。
- 分离“专家观察有效”和“动作执行成功”。保留有效 findings、来源和原拒绝回执，任务终态仍反映未完成的必要动作，不能通过把失败步骤改成 completed 掩盖缺口。
- 将 `unavailable_or_not_allowed` 拆成固定码：`prerequisite_not_met`、`unknown_knowledge`、`tool_not_allowed`、`practice_already_prepared`、`question_unavailable`。仅返回当前学习者允许公开的缺口信息。

不跳过前置知识、不自动补写掌握度，也不为让 L04 通过而更改原场景。

### 5. 总预算有余量，局部调用仍被低价值工具消耗

专家上限为 3 次模型请求、4 次工具；L06 先调用知识上下文、学习者画像、搜索，第 4 个工具读取第一条来源，第 5 个读取被跳过，之后重规划又因执行预算不足被拒绝。L01、L02 也各出现一次工具跳过。知识状态和画像已在专家输入中提供，但前置知识/材料状态没有完整快照，不能把所有上下文读取都认定为重复。[专家输入与循环](../../../python/core/specialist_runtime.py#L92-L176)、[预算实现](../../../python/core/coordination_budget.py)、[逐事件证据](evidence.json)。

优化以减少必要路径的调用为先：

- 一次提供知识状态、前置关系、材料可用性和稳定画像，并标记快照来源/版本；工具用于获取尚缺事实。
- 历史诊断优先“搜索 → 读取来源 A → 读取来源 B”，三次工具即可满足这类任务的核心来源要求；余下额度留给查询恢复或补充。
- 专家每次请求都看到剩余额度，不能只在工具关闭时才获知。缓存命中仍会消耗当前调用额度，优先在消息层避免重查。
- 按任务必要性选择专家。已补充时长和目标但缺正式样文的 L02，可以先给明确标注未诊断的 Curriculum → Tutor 计划；没有必要为了固定三角色链路安排一次无法成立的诊断。
- 失败后先检查剩余额度能否完成新路径，再花请求生成重规划。对于动作不可用，优先使用结构化失败原因交付保守说明，避免重新启动完整诊断。

保留现有 45 秒、8 次父模型调用、16 次父工具调用、3 次委派和 1 次重规划边界。先评估调用顺序与结果契约；只有证据显示必要路径仍不可达，再单独评估预算调整。

### 6. 评分需要区分接续正确与业务交付完成

L02 正确恢复了同一 thread/plan、使用新 session、关闭原 pending，但最终为 `status=completed`、`outcome=partial`，回复没有可执行写作安排。`plan_resolved` 只接受 completed/awaiting_student 状态，因此原评分通过。这里的 completed 表示工作流结束，不等于业务完成；无需首先重命名整个状态机。[评分器](../../../python/evals/long_task_scorers.py#L80-L94)、[最终状态](../harness-long-runs/20261027-deepseek-flash/result.json)。

下轮评分应分别报告：

- **接续合同**：thread/plan 一致、原 pending 被正确关闭。
- **任务交付**：完成所需产物；若允许等待，必须是有必要问题或可继续练习的明确等待态。
- **证据合同**：历史诊断引用已读原文，受助作答不更新独立掌握度。

L02 仅“又进入 awaiting_student”不能自动算最终成功。冻结新评分版本后，用同一版本离线重算两轮作为派生结果，保留原评分与报告，避免事后更换口径造成假提升。

## 优先级与实施边界

| 顺序 | 修改范围 | 主要目的 | 进入下一步的条件 |
| --- | --- | --- | --- |
| P0-1 | 细分校验/动作错误码；修正评分分层 | 下次失败能准确定位，partial 不再当完整成功 | 错误贯通 Trace；L02 原结果在新业务口径下不通过 |
| P0-2 | PlanDraft/专家草稿；服务端证据绑定；否定句校验 | 降低生成接口与执行契约的落差 | 合法输出无需猜服务端字段；伪造来源和状态仍被拒绝 |
| P1 | 历史可访问性摘要、查询扩展、受限枚举、必要澄清 | 先用已有证据，避免无意义等待 | 不靠评测关键词也能找到相关历史；枚举不冒充全文读取 |
| P1 | 可学性快照/预检；区分必要与可选动作；保留有效发现 | 防止可选备题使整个计划失败 | 原 L04 动作仍被门禁拒绝，但有效计划可以继续交付 |
| P2 | 精简专家路径、剩余额度提示、重规划事前可行性 | 在现有边界内为证据与结论留余量 | 两条必要来源可在 4 个工具内读取；修正不超父预算 |
| P2 | 回复采用计划约束与受助标记 | 让学生看到的承诺符合真实状态 | L04 明确先独立限时再提示；L05 不承诺受助表现更新独立掌握 |

这些改动都围绕现有协调、检索、工具和提交链路。没有实施 GEPA、替换模型、扩大并发或重写 Harness 的必要证据。所有方案都是待实施建议，本报告未执行这些生产改动。

## 下轮验证与验收

| L01 | 至少读两条冻结历史；周计划遵守每日 15 分钟及短例子偏好；准备练习并进入等待 |
| L02 | 同一学习线程和计划恢复、原问题关闭；交付每天 20 分钟的主题句/支撑句写作安排，不能只有 partial 回复 |

| L04 | 原话记忆跨重启保留；计划体现“先自己限时完成，再看提示”；无前置掌握时不直接备略读题 |
