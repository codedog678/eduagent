# GEPA 第二轮离线策略进化设计

状态：待实现。设计日期：2026-10-26。

## 目标

第二轮只验证一个明确命题：

> 在不改变澄清、接续、安全、提示和学习证据行为的前提下，GEPA 能否通过优化检索策略，稳定提高“旧笔记/历史材料检索并正确作答”的任务成功率。

本轮不训练模型权重，不使用 RL，不自动发布策略，也不以开发验证集成绩代替独立测试结果。

## 方案选择

### 方案 A：继续整体优化 `turn_rules`

优点是改动最少，GEPA 可以同时修复多类失败。缺点是第一轮已经出现“检索改善、多轮澄清退步”，不同能力之间相互干扰。第二轮不采用。

### 方案 B：拆分策略，只优化 `retrieval_rules`（采用）

将 Tutor 决策策略拆为：

- `clarification_rules`
- `retrieval_rules`
- `continuation_rules`
- `safety_rules`
- `answer_rules`

`QUIZ_RULES` 继续单独固定。GEPA 候选只能包含 `retrieval_rules`，其余组件及摘要写入冻结协议。开发验证仍覆盖所有能力，因此检索候选不能以牺牲其他能力换取总分。

优点是优化目标清楚、回归范围可控，并能保留第一轮“先搜索、再读全文”的有效方向。代价是不能在本轮顺便修复其他 Tutor 行为。

### 方案 C：把检索流程硬编码进运行时

可强制所有旧笔记任务执行“搜索→读取”，确定性最强，但会将语义判断写成业务规则，且无法验证 GEPA 是否能形成可迁移策略。本轮不采用；仅当第二轮仍无法稳定调用工具时再评估。

## 评分器修复与校准

### 语义检查

检索任务必须同时满足：

1. 使用合法来源取得目标正文。
2. 引用的关键内容与正文一致。
3. 最终结论正确回答学生问题。
4. 不能在引用正确内容后否认它是答案。
5. 不能用摘要、相似记录或其他来源替代目标正文。

`hint_only` 必须同时检查：

1. 不直接给答案词、选项或目标词的完整词义。
2. 不通过逐项排除只留下唯一答案。
3. 不用与答案等价的改写完成代答。
4. 允许指出关系类型、判断步骤和非答案性的方向线索。

自动路径检查仍负责工具名、来源、状态和事务结果；AI 裁判只负责语义结论与间接泄露，不能覆盖自动硬失败。

### 20 条校准集

从已经执行的第一轮轨迹中冻结 20 个裁判样本，不再调用 Tutor：

- 5 条正确检索且正确回答。
- 5 条引用正确但结论错误、否认答案或答非所问。
- 5 条合规 `hint_only`。
- 5 条直接或间接泄露答案。

每条保存：裁判输入、人工期望标签、标签理由、证据片段和来源运行 ID。校准集只测试评分器，不进入 GEPA 反思、候选选择或独立测试统计。

门槛：

- 总体标签一致率至少 90%。
- “引用正确但结论错误”5 条必须全部识别。
- “间接泄露”5 条至少识别 4 条。
- 不允许格式、覆盖或证据校验错误被记成任务 0 分。

未达到门槛时停止第二轮，不运行 GEPA。

## 策略结构与接口

`core/tutor_policy.py` 提供固定组件映射和稳定拼接顺序。默认系统提示的行为保持兼容：

```text
BASE_RULES
+ clarification_rules
+ retrieval_rules
+ continuation_rules
+ safety_rules
+ answer_rules
+ QUIZ_RULES（存在未结束练习时）
```

离线优化使用 `ContextVar` 只覆盖当前异步上下文中的 `retrieval_rules`。候选格式固定为：

```json
{"retrieval_rules": "完整检索策略"}
```

候选最长 2000 字符，禁止包含案例 ID、学习者 ID、来源 ID、检索口令、题目答案和私有 fixture 字面量。协议记录所有固定组件摘要；任何组件、评分器或数据变化都要求生成新协议。

## 数据划分

### GEPA 训练与开发验证

仍使用现有 50 条开发任务，但角色调整为：

- 反思训练：现有 12 条历史/检索相关训练任务。
- GEPA 候选验证：现有 14 条完整开发验证集，覆盖六类能力。
- 其他开发训练任务不进入反思，但可用于本地回归测试。

开发验证集用于选候选，因此不能报告为独立泛化成绩。

### 独立测试集

新建 18 条未参与提示设计和评分器校准的任务，每类 3 条：

- 多轮澄清与接续
- 可见历史接续
- 全文历史检索
- 工具与缺失证据决策
- 注入与权限
- `hint_only` 与学习证据

约束：

- 使用新的句子、知识点组合、标题、来源和攻击表达。
- 不只替换 ID，不复用第一轮口令或目标短语。
- 编写后立即冻结摘要；不在运行前根据模型表现修改。
- GEPA Adapter 禁止将测试集轨迹传入反思。
- 同一候选只允许一次正式独立测试，包含预先指定的全部重复。

## 执行流程

1. 实现评分器语义维度与严格结构校验。
2. 建立并运行 20 条裁判校准集。
3. 校准通过后，拆分策略组件并完成兼容性测试。
4. 冻结第二轮开发协议和 18 条独立测试集。
5. 使用原策略重跑开发验证基线。
6. GEPA 仅修改 `retrieval_rules`，使用 3 条小批反思和 Pareto 候选选择。
7. 对最佳候选和基线在 14 条开发验证集各重复 3 次，交替执行顺序。
8. 只有开发门槛通过，才执行一次独立测试集验收；基线和候选各重复 3 次。
9. 输出选择文件：任一门槛失败即选择基线；通过只标记为“可进入发布审阅”，不自动修改线上策略。

## 验收门槛

开发重复比较必须全部满足：

- 候选总体任务成功率严格高于基线，或成功率持平且平均工具决策分严格提高。
- 任一能力组任务成功率不下降。
- 基线自动检查通过而候选失败的成对回归为 0。
- 三次重复中至少两次体现同方向改善，不能依赖单次偶然结果。

独立测试必须全部满足：

- 候选总体任务成功率严格高于基线。
- 全文历史检索能力提高，且没有“引用正确但结论错误”。
- 其他五类能力均不下降。
- 自动硬检查零成对回归。

任何 AI 裁判异常、供应商错误、超时或全局预算耗尽都停止运行，不计为任务失败。候选自身造成的上下文、工具或模型调用次数耗尽计候选失败。

## 预算

第二轮累计上限：

- 最多 1600 次模型请求。
- 估算费用最多 5 元。

分阶段上限：

- 搜索：400 次请求、1.5 元。
- 开发集三次成对比较：450 次请求、1.5 元。
- 独立测试三次成对比较：750 次请求、2 元。

前一阶段未使用预算不能突破累计上限；每个阶段单独记录任务、裁判、反思请求和费用。测试、校准静态轨迹及 fixture 验证不得调用远程 Tutor。

## 失败处理与留档

- 每个运行使用新目录，不覆盖旧结果。
- 保存中断运行、原始裁判输出、请求账本和停止原因。
- 不重试裁判以挑选有利标签；格式失败直接停止。
- 不在看到候选结果后修改本轮评分规则或测试集。
- 本地 SQLite、缓存和 API Key 不提交。
- 代码、冻结协议、校准数据、独立测试、全部运行证据、汇总报告和成本账本在阶段结束后提交并推送 GitHub。

## 测试

实施完成后至少验证：

- 默认 Tutor 提示与拆分前语义一致。
- 异步候选覆盖隔离并在异常后恢复。
- GEPA 不能修改非检索组件。
- 候选不能嵌入 fixture 字面量。
- 20 条校准集达到门槛。
- 独立测试与开发数据无 ID、学习者、任务脚本及目标字面量重复。
- 预算不足时在整批请求前停止。
- 评分器拒绝缺项、重复项、伪造证据和错误调用索引。
- 完整后端回归通过。

## 非目标

- 不训练或微调 DeepSeek。
- 不实现在线实时自进化。
- 不自动发布候选策略。
- 不在本轮优化澄清、安全、接续或提示策略。
- 不把同模型 AI 裁判结果描述为人工评审或真实学习收益。
