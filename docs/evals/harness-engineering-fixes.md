# Harness 长任务工程修复

日期：2026-10-26。状态：已实现，离线回归通过。范围由用户确认：先修改工程链路，不进行策略进化。

## 修改边界

保留现有 45 秒、8 次模型调用、16 次工具调用及 3 次委派上限。冻结数据和历史评测记录不变。本轮验证使用脚本模型，不调用真实供应商或 GEPA。

直接修复现有协议优于扩大配额：配额扩大无法解决错误折叠与丢失待答状态；重写调度器则超出当前缺陷范围。

## 设计

1. 委派失败通过稳定错误码传递。专家预算、输出 schema、来源校验及工具参数问题分别记录，公开信息只含代码和异常类型，不包含原始异常文本。父运行超时和供应商错误仍交 Harness 回滚。
2. 规划、重规划和每次委派前检查剩余链路预算。每个剩余专家至少留一次结论请求，Tutor 按现有配置保留额度；明确要求备题时另留一次生成额度。可行时动态分配专家上限；不可行时输出带缺口的部分结果。
3. 专家最后一次请求关闭工具并要求输出结构化结论；工具额度不足的调用返回预算结果，不执行超额工具。请求数、工具数及只读重试仍受父运行硬上限约束。
4. 同一 learner/thread 的等待计划优先恢复；只有待答问题时优先接续 Tutor，不因新 session 或新任务措辞新建计划。无待答状态时才使用任务意图匹配。
5. 扩展“检索/诊断后生成计划”等同义路由，同时保留历史计划查询的普通答疑语义。
6. 规划器与专家直接接收有效、按 learner 隔离的偏好/目标事实及来源。规划协议支持结构化证据槽和必要澄清；声明已存在的偏好/目标缺失时拒绝计划并使用带真实约束的保守计划。读取证据仍不得执行历史内指令。
